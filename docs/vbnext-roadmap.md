# Vb.Next roadmap

**Vb.Next** is an independent community effort to explore modern Visual Basic language features on top of the [Roslyn](https://github.com/dotnet/roslyn) compiler. It is not affiliated with, endorsed by, or supported by Microsoft. "Visual Basic", ".NET", and "Roslyn" are used here only to identify the upstream project this fork builds on.

The project name is tentative. This document is a planning note only. It does not specify a finished language design, and it does not implement a language feature.

## Branch policy

| Branch | Role |
| --- | --- |
| `main` | Clean sync of [dotnet/roslyn](https://github.com/dotnet/roslyn) `main`, as published on this fork. Do not land experiments here. |
| `vbnext/main` | Experimental Vb.Next work, including this roadmap. |

Upstream merges should land on `main` first. `vbnext/main` should take those updates by merge or rebase only after the experimental diff is understood. The files most likely to conflict are called out under [Compatibility risks](#compatibility-risks).

The tree inspected for this note is `main` commit `8bd473fe` (`Remove legacy pull diagnostics methods`). On that commit, `LanguageVersion.Latest` and `LanguageVersion.Default` both map to `VisualBasic17_13`.

## Where Visual Basic language features live

Visual Basic is a parallel compiler inside this repo, not a mode of the C# compiler. The implementation is concentrated in `src/Compilers/VisualBasic`. IDE, scripting, and the command-line host sit beside it and must be considered before a feature is treated as usable.

A new syntactic or semantic feature normally crosses these stages, in order:

1. **Language version gate.** `src/Compilers/VisualBasic/Portable/LanguageVersion.vb` defines `LanguageVersion`, parses `/langversion` strings, and maps `Default` and `Latest` to a concrete version. `VisualBasicParseOptions` stores the specified and effective versions. `src/Compilers/VisualBasic/Portable/Parser/ParserFeature.vb` is the feature enum: each `Feature` value names the `LanguageVersion` that enables it and the `ERRID` reported when it is used too early.
2. **Command line.** `src/Compilers/VisualBasic/Portable/CommandLine/VisualBasicCommandLineParser.vb` accepts `/langversion`. The `vbc` host under `src/Compilers/VisualBasic/vbc` is a thin driver over that parser.
3. **Scan.** `src/Compilers/VisualBasic/Portable/Scanner/` tokenizes source. `KeywordTable.vb` registers keyword kinds and the flags that say where a keyword may appear. Literals, interpolated strings, and XML tokens are special cases in this folder.
4. **Parse.** `src/Compilers/VisualBasic/Portable/Parser/` turns tokens into the green syntax tree (`Parser.vb`, `ParseStatement.vb`, `ParseExpression.vb`, and the specialized parse files). New grammar should be rejected here when the effective language version is too low.
5. **Syntax model.** `src/Compilers/VisualBasic/Portable/Syntax/Syntax.xml` is the source of truth for syntax node shape. `eng/generate-compiler-code.cmd` regenerates factories, visitors, and `SyntaxKind` from it. Hand-editing generated syntax files will drift from the XML.
6. **Declarations.** `src/Compilers/VisualBasic/Portable/Declarations/` builds the declaration tree that symbol binding consumes.
7. **Symbols.** `src/Compilers/VisualBasic/Portable/Symbols/`, especially `Symbols/Source/`, represents types, members, and synthesized members.
8. **Bind.** `src/Compilers/VisualBasic/Portable/Binding/` produces the bound tree. Conversions, overload resolution, and type inference live in `src/Compilers/VisualBasic/Portable/Semantics/`.
9. **Bound tree.** `src/Compilers/VisualBasic/Portable/BoundTree/BoundNodes.xml` describes bound nodes and is also regenerated by `eng/generate-compiler-code.cmd`.
10. **Lower.** `src/Compilers/VisualBasic/Portable/Lowering/` rewrites bound trees into a simpler form (lambdas, iterators, async, `With`, and similar).
11. **Emit.** `src/Compilers/VisualBasic/Portable/CodeGen/` and `Emit/` write IL. They sit on the shared compiler in `src/Compilers/Core` and `src/Compilers/Shared`.
12. **Diagnostics.** New errors need an `ERRID` in `src/Compilers/VisualBasic/Portable/Errors/Errors.vb`, text in `VBResources.resx`, and localization entries under `xlf/`.

Tests for that pipeline are split by layer:

- `src/Compilers/VisualBasic/Test/Syntax`
- `src/Compilers/VisualBasic/Test/Semantic`
- `src/Compilers/VisualBasic/Test/Symbol`
- `src/Compilers/VisualBasic/Test/Emit`
- `src/Compilers/VisualBasic/Test/CommandLine`
- `src/Compilers/VisualBasic/Test/IOperation`

`docs/Language Feature Status.md` records what upstream has already shipped. Its "Working Set VB" section is empty on this commit. The latest Visual Basic entries there are consumption-oriented: the `unmanaged` constraint and overload-resolution priority in the VB 17.13 / .NET 10 section, caller-argument-expression support in VB 17.0, and consumption of init-only setters in VB 16.9. `docs/features/` is mostly C# design notes. Visual Basic compiler notes live under `docs/compilers/Visual Basic/`.

## Compiler areas a feature is likely to touch

The areas below are the ones a Vb.Next change should expect to edit. Prefer to stay inside `src/Compilers/VisualBasic` until a feature truly needs shared infrastructure.

| Kind of change | Likely areas |
| --- | --- |
| Versioning only | `LanguageVersion.vb`, `ParserFeature.vb`, `VisualBasicParseOptions.vb`, `VisualBasicCommandLineParser.vb`, command-line tests |
| New keyword or literal | `Scanner/KeywordTable.vb`, `SyntaxKind` via `Syntax.xml`, parser, classifier in Workspaces |
| New expression or statement | `Parser/ParseExpression.vb` or `ParseStatement.vb`, `Syntax.xml`, `Binding/`, often `BoundNodes.xml`, lowering and codegen if the construct does not reuse an existing bound node |
| New type or member shape | `Declarations/`, `Symbols/Source/`, `Binding/`, `Emit/`, public API surface |
| New conversion or overload rule | `Semantics/Conversions.vb`, `Semantics/OverloadResolution.vb`, `Semantics/TypeInference/` |
| Diagnostic text | `Errors/Errors.vb`, `VBResources.resx`, `xlf/` |
| Public compiler API | `PublicAPI.Shipped.txt` and `PublicAPI.Unshipped.txt` on `Microsoft.CodeAnalysis.VisualBasic` |

Shared code in `src/Compilers/Core` is also the C# compiler's metadata reader, emitter, and well-known-member table. A Visual Basic feature that needs a new well-known attribute or a new IL pattern may need a Core change. That change can break C# in the same tree, so it should be isolated and tested on both languages.

## IDE and tooling that sit on the compiler

A compiler-only change can still leave the product unusable. These trees mirror Visual Basic and assume the current syntax and symbols:

- `src/Workspaces/VisualBasic/Portable` — classification, formatting, rename, code generation, simplification
- `src/Features/VisualBasic/Portable` — completion, quick info, signature help, code fixes, refactorings, Edit and Continue
- `src/EditorFeatures/VisualBasic` — End-construct insertion, line commit, brace completion, navigation
- `src/ExpressionEvaluator/VisualBasic` — the debugger expression evaluator
- `src/Scripting/VisualBasic` and `src/Interactive/vbi` — scripting and the interactive host
- `src/Compilers/VisualBasic/Portable/Emit/EditAndContinue` — compiler EnC deltas

`src/Compilers/VisualBasic/Portable/SourceGeneration/VisualBasicGeneratorDriver.vb` is the source-generator entry point. Generators written against today's syntax trees will break if node shape or `SyntaxKind` values change.

## First candidates to investigate

These are investigation targets, in the order they should be studied. None of them is approved syntax. The first investigation should produce a short design note and tests of the existing gate, not a new construct.

1. **Language-version plumbing.** Confirm how `LanguageVersion`, `Feature`, `/langversion`, MSBuild `LangVersion`, and `PublicAPI.*.txt` move together. Upstream `Latest` is `17.13`. Any experimental version has to be opt-in so that `default` and existing projects keep today's behavior. This is the gate every later feature will use.
2. **Target-typed `New`.** Visual Basic already parses and binds `New`. A target-typed form is an expression-level change: parser, object-creation binding, and conversions. It is a useful first real feature because it can reuse `BoundObjectCreationExpression` instead of inventing a new declaration or metadata encoding. IDE impact is mostly completion and formatting.
3. **Declaring init-only properties.** VB 16.9 already *consumes* init-only setters (`Feature.InitOnlySettersUsage` in `ParserFeature.vb`). Declaring them is the next step and stays inside symbols, binding, and emit. It is a prerequisite for any later record-like design, and it has a metadata contract (`init` accessors, `IsExternalInit`) that must match the runtime the C# compiler already emits.
4. **Richer `Select Case` patterns.** `Binding/Binder_SelectCase.vb` and the case-clause bound nodes are the existing pattern surface. Extending them teaches the bound-tree and lowering path without taking on nullable reference types or records. Classification, highlighting, and formatting in Workspaces and Features will need a pass if the grammar grows.

Later, and only after the four items above are understood:

- **Raw string literals.** Scanner and interpolated-string parsing, plus classification. Visual Basic already has multiline string literals from VB 14, so the design has to say how a new literal differs.
- **Required members.** Symbol and emit work with an existing metadata attribute. Depends on object-initializer binding.
- **Nullable reference types and records.** These cut across symbols, binding, public API, IDE, and metadata. They are poor first features. Nullable annotations also collide with Visual Basic's existing `?` nullable value-type syntax, so the design problem is larger than the C# one.

`docs/Language Feature Status.md` should be treated as the upstream inventory. Vb.Next should not re-implement a feature that section already lists as merged for Visual Basic.

## Compatibility risks

### Keeping `main` buildable

Experiments belong on `vbnext/main` or on short-lived branches cut from it. `main` has to stay a branch that can fast-forward to upstream. Mixing experimental commits into `main` makes the sync unusable.

### Public API and package identity

`Microsoft.CodeAnalysis.VisualBasic` is a public NuGet surface. New `LanguageVersion` values, syntax nodes, and semantic APIs show up in `PublicAPI.Shipped.txt` / `PublicAPI.Unshipped.txt` (and in the matching files for Workspaces and Features). Downstream source generators, analyzers, and the IDE compile against that surface.

Shipping a fork under the same assembly and package identity as Microsoft.CodeAnalysis can be loaded in place of the official compiler by mistake. Vb.Next builds that leave this repo need their own package ids and versions before anyone is asked to install them. That packaging decision is out of scope for this note.

### SDK, `vbc`, and the compiler server

`dotnet build` does not use whatever compiler happens to be checked out here. The .NET SDK selects a compiler toolset. Until a project is pointed at a Vb.Next toolset, `/langversion` values this fork invents will be rejected by the stock `vbc`. The in-box compiler server (`src/Compilers/Server`) caches compiler builds; mixing a forked server with a stock one will produce confusing diagnostics.

### IDE and Edit and Continue

Visual Studio, the Visual Basic language service, and the debugger expression evaluator ship their own Roslyn build. A fork that changes syntax or bound-tree shape will not light up in that IDE. Completion, End-construct insertion, classification, and Edit and Continue can throw or mis-color code when they see nodes they do not know. EnC is especially sensitive to bound-node identity in `Emit/EditAndContinue`.

### Generated sources and resources

`Syntax.xml` and `BoundNodes.xml` must be regenerated with `eng/generate-compiler-code.cmd`. Error strings must stay consistent across `Errors.vb`, `VBResources.resx`, and `xlf/`. These files are also where upstream merges conflict most often.

### IL and cross-language metadata

New features should lower to IL and metadata the existing runtime already understands. Changing the encoding of constructs Visual Basic already emits will break assemblies compiled by the stock compiler, and it will break C# consumers of those assemblies. Shared edits under `src/Compilers/Core` need C# test coverage as well as Visual Basic coverage.

### Determinism and tests

The compiler has deterministic-build requirements (`VisualBasicDeterministicKeyBuilder`, `docs/compilers/Deterministic Inputs.md`). A feature that reads ambient state, or that emits members in an unstable order, will fail those checks. New behavior needs tests in the layer that implements it: syntax tests for the grammar, semantic tests for binding, emit tests for IL, and command-line tests for `/langversion`.
